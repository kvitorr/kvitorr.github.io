Introdução à Mensageria com RabbitMQ (Parte 1 – Conceitos)

10 Set 2025 · 8 min read

Ao final deste artigo, espera-se que você seja capaz de:

  • Definir mensageria e entender seu objetivo;
  • Explicar a relação entre mensageria, sistemas de mensagem e um message broker;
  • Identificar os componentes fundamentais de um sistema de mensagem;
  • Reconhecer e diferenciar os termos message broker, producer, consumer, exchange, queue, binding, listener, mensagem e topologia.

Introdução

Quando navegamos na Internet, realizamos constantemente trocas de informações: recebemos o conteúdo de um site, enviamos dados por meio de formulários ou acionamos serviços ao clicar em botões.

Em determinadas situações, a prioridade é a velocidade da transmissão, mesmo correndo o risco de perda de pacotes.

Por exemplo, em videoconferências, para garantir comunicação em tempo real, voz e vídeo são enviados via protocolo UDP, que não assegura a entrega íntegra dos pacotes, o que pode resultar em queda de qualidade de imagem ou distorções de áudio.

Já em outras situações, como em arquiteturas de microsserviços, a prioridade é garantir a entrega da informação de um serviço ao outro e é nesse ponto que a mensageria ganha destaque.

O que é mensageria, sistema de mensagem e message broker?

O termo Mensageria é utilizado para descrever o processo de comunicação entre sistemas, componentes de software ou serviços através do envio e recebimento de mensagens.

Ao utilizarmos esse termo, não estamos fazendo referência a uma ferramenta específica mas sim ao mecanismo que possibilita a comunicação síncrona ou assíncrona entre sistemas distribuídos.

As mensagens enviadas e recebidas são blocos de dados (geralmente binários ou em formatos como JSON) definidos pelo desenvolvedor.

Para implementar essa comunicação em um sistema real, precisamos de uma infraestrutura capaz de aplicar esse mecanismo na prática.

E é aí que entra o sistema de mensagem que oferece recursos para:

  • Criação, transmissão, armazenamento e entrega de mensagens entre aplicações
  • Protocolos de transporte (AMQP, MQTT, STOMP)
  • APIs e SDKs para produção e consumo
  • Suporte a filas, tópicos e roteamento
  • Message broker

Como exemplo de sistema de mensagens, temos o RabbitMQ que suporta os protocolos AMQP, MQTT e STOMP. E também possui um message broker, componente responsável por receber, armazenar e encaminhar as mensagens entre os produtores e consumidores.

Observação: Tecnicamente, o message broker do RabbitMQ é apenas uma parte do sistema de mensagens. Mas no dia a dia, costuma-se chamar o RabbitMQ diretamente de broker.

Diagrama de um Sistema de Mensagem

Agora que entendemos os principais conceitos, fica mais fácil visualizar esse processo em funcionamento. No diagrama abaixo, é possível acompanhar o caminho percorrido por uma mensagem: da aplicação produtora, passando pelo message broker (exchange e queue), até chegar ao consumidor que processa a informação e retorna o resultado para a aplicação final.

  1. A camada de negócio chama o componente produtor
  2. O produtor envia a mensagem para uma exchange do message broker
  3. A exchange roteia a mensagem para uma ou mais filas
  4. O consumidor lê da fila e processa a mensagem
  5. O resultado do processamento é utilizado pela aplicação

No diagrama observamos o fluxo da mensagem desde o produtor até o consumidor. Dentro do próprio message broker, como você deve ter percebido, existem elementos que fazem esse processo acontecer de forma organizada.

Componentes dentro do Message Broker

A exchange recebe as mensagens enviadas pelo produtor e decide para onde cada uma deve seguir. Ela não armazena dados, apenas encaminha a mensagem com base em regras definidas.

Em seguida, temos a queue, que funciona como uma fila de espera. As mensagens ficam armazenadas nela até que algum consumidor esteja disponível para processá-las.

A ligação entre uma exchange e uma fila é chamada de binding. É através dessa configuração que o broker entende quais mensagens devem ser direcionadas para cada fila. Essa organização envolve as exchanges que estão presentes e o tipo de cada uma delas, como direct, fanout, topic ou headers (tópico que possivelmente será discutido em alguma postagem futura).

Consumo de mensagens na aplicação

A mensagem que chega à fila é processada por um consumidor. Na aplicação, esse papel costuma ser implementado por um listener que escuta a fila e, ao receber uma nova mensagem, executa a lógica de negócio. Com o processamento bem-sucedido, o consumidor envia um ACK ao broker, que então remove a mensagem da fila.

Observação: ACK é um sinal confirmando o processamento com sucesso da mensagem.

Essa relação entre exchange, queue, binding e listener e a forma como eles se organizam dentro do sistema de mensagem é chamada de topologia. A topologia mostra quais exchanges existem e seus tipos, quais filas recebem mensagens, como os bindings conectam cada exchange às filas e quais consumidores estão ligados a cada uma delas.

Com isso, conseguimos modelar desde cenários simples, em que existe apenas uma fila consumida por um único serviço, até arquiteturas complexas, em que várias exchanges distribuem mensagens para diferentes filas e consumidores especializados.

Pensar na topologia é essencial porque ela define o caminho da informação dentro do sistema e garante que cada mensagem chegue ao destino correto.

Conclusão

Nesta primeira parte, organizamos os conceitos: produtor, exchange, fila, binding, listener e topologia. Com os termos claros e o percurso da mensagem bem entendido, implementar a topologia em código fica muito mais simples. Na parte dois, vamos para a prática com Java e RabbitMQ.

Introduction to Messaging with RabbitMQ (Part 1 – Concepts)

Sep 10, 2025 · 8 min read

By the end of this article, you should be able to:

  • Define messaging and understand its purpose;
  • Explain the relationship between messaging, messaging systems, and a message broker;
  • Identify the core components of a messaging system;
  • Recognize and differentiate the terms message broker, producer, consumer, exchange, queue, binding, listener, message, and topology.

Introduction

When we browse the Internet, we constantly exchange information: we receive content from a website, submit data through forms, or trigger services by clicking buttons.

In some situations, the priority is transmission speed, even at the risk of packet loss.

For example, in video calls, to ensure real-time communication, voice and video are sent over UDP, which does not guarantee full packet delivery. This can result in lower image quality or audio distortion.

In other scenarios, such as microservice architectures, the priority is to guarantee that information is delivered from one service to another, and that's where messaging stands out.

What is messaging, a messaging system, and a message broker?

The term Messaging describes the process of communication between systems, software components, or services through sending and receiving messages.

When we use this term, we're not referring to a specific tool but rather to the mechanism that enables synchronous or asynchronous communication between distributed systems.

The messages sent and received are data blocks (usually binary or in formats like JSON) defined by the developer.

To implement this communication in a real system, we need an infrastructure capable of applying this mechanism in practice.

That's where the messaging system comes in, offering features for:

  • Creating, transmitting, storing, and delivering messages between applications
  • Transport protocols (AMQP, MQTT, STOMP)
  • APIs and SDKs for producing and consuming
  • Support for queues, topics, and routing
  • Message broker

As an example of a messaging system, RabbitMQ supports the AMQP, MQTT, and STOMP protocols. It also includes a message broker, the component responsible for receiving, storing, and forwarding messages between producers and consumers.

Messaging System Diagram

Now that we understand the key concepts, it's easier to visualize how this process works. In the diagram below, you can follow the path a message takes: from the producer application, through the message broker (exchange and queue), to the consumer that processes the information and returns the result to the final application.

  1. The business layer calls the producer component
  2. The producer sends the message to an exchange in the message broker
  3. The exchange routes the message to one or more queues
  4. The consumer reads from the queue and processes the message
  5. The processing result is used by the application

In the diagram, we can see the message flow from producer to consumer. Inside the message broker itself, as you may have noticed, there are elements that make this process happen in an organized way.

Components Inside the Message Broker

The exchange receives messages sent by the producer and decides where each one should go. It doesn't store data, it only forwards messages based on defined rules.

Next, we have the queue, which works like a waiting line. Messages are stored there until a consumer is available to process them.

The connection between an exchange and a queue is called a binding. It's through this configuration that the broker knows which messages should be directed to each queue. This organization involves the exchanges that are present and the type of each one, such as direct, fanout, topic, or headers (a topic that will possibly be discussed in a future post).

Message Consumption in the Application

The message that reaches the queue is processed by a consumer. In the application, this role is usually implemented by a listener that watches the queue and, upon receiving a new message, executes the business logic. When processing is successful, the consumer sends an ACK to the broker, which then removes the message from the queue.

Note: ACK is a signal confirming the successful processing of a message.

This relationship between exchange, queue, binding, and listener, and the way they are organized within the messaging system, is called topology. The topology shows which exchanges exist and their types, which queues receive messages, how bindings connect each exchange to queues, and which consumers are connected to each one.

With this, we can model anything from simple scenarios, where a single queue is consumed by one service, to complex architectures where multiple exchanges distribute messages to different queues and specialized consumers.

Thinking about topology is essential because it defines the path of information within the system and ensures that each message reaches the correct destination.

Conclusion

In this first part, we organized the concepts: producer, exchange, queue, binding, listener, and topology. With the terms clear and the message path well understood, implementing the topology in code becomes much simpler. In part two, we'll get hands-on with Java and RabbitMQ.
